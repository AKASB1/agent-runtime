# Contracts, version 1

`contracts_version: 1`. This document is the binding, language-neutral definition of the formats, rules, and definitions of `agent-runtime`, so that a reader does not need the Python package. Changes are deliberate, versioned, and logged. The conventions follow version 1 of the conventions of the owner's projects `llm-serving-control` (its `docs/contracts.md`, sections 1-2) and `gpu-cluster-scheduler` (section 1); they are restated here so this document stands alone. No code is shared with those projects.

All results produced under these contracts are **simulated**: the models' accuracies, prices, and latencies are assumptions (section 10), not measurements of any model.

## 1. Conventions

- **Time.** Domain code reads time only from an injectable `Clock` (integer milliseconds since the start of the run or the process) and waits only through it: a virtual clock for simulations and tests, the system clock or a scaled one otherwise (`--time-scale k`: k virtual ms per real ms). Simulations run on a virtual-time event loop whose `time()` is the virtual time and whose selector, instead of blocking, advances the virtual time to the next timer. Timers due at the same virtual time run in the order (time, sequence number). A zero-length wait does not yield. That loop supports neither sockets nor subprocesses; the tests of MCP, the exec tool, the API, and the stand-in server use the default loop and the system clock, and their traces carry timestamps that byte comparisons exclude.
- **Randomness.** One stream per component: `random.Random(splitmix64(seed XOR fnv1a64(name)))`, using only `random()` (and `getrandbits()`), whose output is stable across CPython versions. `fnv1a64` is 64-bit FNV-1a over the UTF-8 bytes of the name; `splitmix64` is the standard SplitMix64 output function (add `0x9e3779b97f4a7c15`, xor-shift-multiply by `0xbf58476d1ce4e5b9` and `0x94d049bb133111eb`). Known answers: `fnv1a64("") = 0xcbf29ce484222325`, `fnv1a64("a") = 0xaf63dc4c8601ec8c`, `splitmix64(0) = 0xe220a8397b1dcdaf`. The streams are not bit-identical to the Go (PCG) streams of the sibling projects. A normal draw is Box-Muller from two `random()` values (`sqrt(-2 ln(1-u1)) cos(2 pi u2)`); a lognormal draw is its exponential. Stream names: a simulated call `sim/<provider>/<model>/<task_id>/<attempt>/<ordinal>`; retry jitter `retry/<run_id>/<ordinal>`; the verifier `verifier/<task_id>/<attempt>`; the difficulty hint `task/<task_id>/hint`; the task generator `gen/<mix>/<shape>`; provider faults `fault/<provider>/<run_id>/<ordinal>`; tool latencies `tool/<run_id>/<n>`; transient tool faults `toolfault/<run_id>/<n>`; random routing `route/<task_id>/<attempt>`; E2 arrivals `arrivals`. A child run extends the task id with `/c<ordinal>`; `summarize` calls use their own ordinals `s<n>`. The global state of `random` and `hash()` never influences a result.
- **Units.** Tokens are integers. Time is integer milliseconds in code and records (`*_ms`), decimal seconds with at most three decimals in reports and API fields named `*_s`. Cost is in cost units (cu), an abstract currency: a price is an integer number of micro-cu (ucu) per million tokens (0.15 cu = 150000 ucu), and a call costs `ceil((tokens_in*price_in + tokens_out*price_out + tokens_cache_read*price_cache_read + tokens_cache_write*price_cache_write) / 1000000)` ucu in integer arithmetic, where `tokens_in` is the uncached input only. Reports show milli-cu (1 mcu = 1000 ucu). Prices are illustrative and not any provider's.
- **Identifiers.** Sessions `s-<n>`, runs `r-<n>`, messages `m-<n>`, compactions `k-<n>`, spans `sp-<n>` (a counter per trace). Store counters are taken inside the transaction that creates the object; every event of a session has a `seq` (1, 2, ...) assigned in the transaction that appends it. A child run has no id of its own. In simulations a run id is `r-<experiment>.<configuration>.<seed>.<task_id>`. No UUID and no timestamp enters a trace.
- **Determinism.** The same configuration, task set, and seed give byte-identical traces and result rows on the virtual clock, for any worker count. Ties break by an explicit total order (timer sequence number, step id, target order of the registry), never by dict or set iteration order. Fields that carry wall-clock measurements start with `wall_` and are excluded from byte comparisons.
- **Errors.** Every API error has the body `{"error": {"code": "...", "message": "...", "details": {}}}` with a stable upper-case `code` (section 12).
- **Defaults** (part of the contract): per-call timeout 10000 ms; retry at most 3 attempts per target, `backoff_base_ms` 200, `backoff_cap_ms` 5000, full jitter `random() * min(cap, base * 2^(n-1))`, a 429 waits at least its `retry_after_ms`; repair budget 2 per step; tool retries 2 (read-only tools only); at most 40 model calls per run; concurrency limit 4; no run deadline; context policy `none`, `compact_at` 0.75, `compact_to` 0.5, `keep_last` 2 exchanges; subagents depth 1, `max_steps` 8, result cap 400 tokens; workspace tools 65536 bytes per file read and per output stream, 262144 bytes per HTTP response, the per-call timeout for `run_command`; permissions sandbox `workspace_write`, approval `never`; max 2 replans; max 20 plan steps.

## 2. Model interface

- `ModelRequest`: `model` (a registry target `provider/model`), `messages` (each: `role` in `system|user|assistant|tool`, `content`, `tool_calls` and optional `reasoning` on assistant messages, `tool_call_id` on tool messages), `tools` (each: `name`, `description`, `parameters` = JSON Schema of the arguments), `response_schema` (JSON Schema or null), `max_output_tokens` (default 512), `timeout_ms`, `meta` (free dictionary that real adapters ignore; the runtime sets `task_id`, `role` (`act`, `plan`, `replan`, `answer`, `formulate`, `report`, `summarize`), `hint`, `attempt`, `ordinal`, `run_id`, `call_ordinal`, and `parallel` for `react_parallel`).
- `ModelResponse`: `text`, `tool_calls` (each `id`, `name`, `arguments` as an object; arguments that are not valid JSON arrive as `{"_invalid_json": "<raw>"}` and fail validation), `finish_reason` (`stop|tool_calls|length`), `usage` (`input_tokens` = the uncached input only; `output_tokens`; `cache_read_tokens`, `cache_write_tokens`, 0 when not reported; `estimated`, true when the adapter estimated the counts), `model`, `provider`, and optional `reasoning`. The runtime measures latency on its own clock and computes cost itself; it never trusts a provider's number for either.
- `ModelSpec` (registry entry): `id`, `provider`, `wire` (`sim`, `scripted`, `openai_chat`; `anthropic_messages` is Tier 2, not built), `dialect` (`openai` or `deepseek` for `openai_chat`; anything else is a configuration error), `price_in_ucu`, `price_out_ucu`, `price_cache_read_ucu` and `price_cache_write_ucu` (both default to `price_in_ucu`), `context_tokens`, `capabilities` (`tools`, `json_schema`), `priced`. A target is offered to the router only when the irreducible part of the request fits its window minus `max_output_tokens` and it has the needed capabilities.
- `ProviderError`: `kind` (closed list: `timeout`, `rate_limited`, `server_error`, `bad_request`, `auth`, `context_length`, `invalid_output`, `tool_error`, `tool_timeout`, `budget_exhausted`, `cancelled`, `permission_denied`, `subagent_failed`), `retryable`, `status`, `retry_after_ms`, `message`. Adapters raise only this.
- **OpenAI-compatible wire (`openai_chat`).** `POST {base_url}/chat/completions` with exactly `model`, `messages`, `max_tokens`, plus `tools` (`{"type": "function", "function": {name, description, parameters}}`) when tools are offered and `response_format` when a schema is requested, plus the dialect's extra fields. Tool-call arguments are JSON strings on the wire. Status mapping: 401, 402, 403 -> `auth`; 408 -> `timeout`; 429 -> `rate_limited` (`retry-after-ms` or `retry-after` header -> `retry_after_ms`); 5xx -> `server_error`; a 4xx whose body mentions the context length -> `context_length`; other 4xx -> `bad_request`; a transport timeout -> `timeout`; a transport error, a body that is not JSON, or a body without `choices[0].message` -> `server_error`; finish reason `insufficient_system_resource` -> `server_error`, `content_filter` -> `stop`.
- **Dialects.** `openai` (also for local OpenAI-format servers such as Ollama or LM Studio): usage `prompt_tokens`, `completion_tokens`, `prompt_tokens_details.cached_tokens` (`input_tokens` = prompt - cached); structured output as `response_format: {"type": "json_schema", ...}`; no reasoning text. `deepseek`: usage `prompt_cache_hit_tokens` and `prompt_cache_miss_tokens` (read at the top level of `usage`, else under `prompt_tokens_details`); `reasoning_content` is parsed and passed back on assistant messages in every later request that carries `tools`, and dropped otherwise; structured output as `response_format: {"type": "json_object"}`. Without a usage block the adapter estimates (UTF-8 bytes / 4, rounded up) and sets `estimated`. Credentials come only from the adapter's configuration object and never appear in errors, logs, or traces.

## 3. Failure table

| Kind | Source | Retry the same target | Fall back to the next target | Otherwise |
|---|---|---|---|---|
| `timeout`, `rate_limited` (waits at least `retry_after_ms`), `server_error` | provider | yes, up to 3 attempts with backoff | after the retries are used up | the step fails with `provider_unavailable` |
| `bad_request` | request | no | no | the step fails with `bad_request` |
| `auth` | configuration | no | yes | the step fails with `auth` |
| `context_length` | request | no | only to a target with a larger window | the step fails with `context_length` (the context manager has already compacted as far as its policy allows; a step whose irreducible part fits no window fails without a call) |
| `invalid_output` | the model's output fails validation | repair: the validation message goes back to the model as a logged user message (budget 2 per step) | then the router names the next model (the current target is excluded) | the step fails with `invalid_output` (`plan_invalid` for plans) |
| `tool_error`, `tool_timeout` | tool | read-only tools (side effect `read` or `none`): up to 2 more times, for timeouts and `UNAVAILABLE`; write tools never | no | the error is the tool result; the model or planner decides |
| `budget_exhausted` | runtime | no | no | the run ends `budget_exhausted` with its partial trace |
| `cancelled` | caller | no | no | the run ends `cancelled`; no new call starts; in-flight calls are cancelled |
| `permission_denied` | permission layer | no | no | the error is the tool result `PERMISSION_DENIED` with the rule id; the tool did not run |
| `subagent_failed` | child run | no | no | the error is the tool result `SUBAGENT_FAILED` with the child's status and reason |

The fallback chain of a step is the router's choice followed by the configuration's `fallback` targets that are offered; after a `context_length` error only targets with a window larger than the largest window that failed are tried. The budget is checked before every provider attempt. A provider error is not billed. An invalid tool call in `react` (unknown tool or arguments that fail validation) is a tool result `UNKNOWN_TOOL` or `INVALID_ARGUMENTS` that counts as a repair of the current step; after more than 2 consecutive repairs the next turn excludes the current target, and if no other target is offered the step fails with `invalid_output`. Tool error codes: `INVALID_ARGUMENTS`, `UNKNOWN_TOOL`, `INVALID_OUTPUT`, `NOT_FOUND`, `UNAVAILABLE`, `TIMEOUT`, `PERMISSION_DENIED`, `FAILED`, `SUBAGENT_FAILED`.

## 4. Runs, sessions, budgets

- Run states: `running`, `succeeded`, `failed`, `cancelled`, `budget_exhausted`. Failure reasons (closed list): `provider_unavailable`, `bad_request`, `auth`, `context_length`, `invalid_output`, `step_failed`, `plan_invalid`, `verifier_rejected`.
- A budget is `deadline_ms`, `max_cost_ucu`, and `max_model_calls`, checked before every model call and tool call; `max_model_calls` counts every provider attempt started. When one is exhausted no new call starts and the run ends `budget_exhausted`.
- A session holds an append-only log of events and a JSON `state` with an integer version; a state write names the version it read, and a mismatch is `VERSION_CONFLICT`. The store (SQLite: WAL, busy timeout, `BEGIN IMMEDIATE` write transactions; an in-memory implementation for simulations) has no update and no delete for events. A run executes inside a session (an implicit one when none is given); runs and traces are stored with their session.
- Attempts: the task workflows run as attempt 1, 2, ... (attempt `a > 1` uses a fresh conversation `a<a>` in the same session log). A final answer goes to the run-time verifier (when one is configured); an attempt that is rejected or fails runs again only when the router escalates (only `cascade` does). A run whose last attempt is rejected ends `failed` with `verifier_rejected`.

## 5. Tools and MCP

- A tool has a `name` (`[a-z][a-z0-9_]{0,47}`; MCP tools `<server>.<tool>`), a description, an input and an output model (MCP tools: the JSON Schema the server declares), `timeout_ms`, `side_effect` (`none|read|write`), and `capability` (`none|fs_read|fs_write|exec|net`). Arguments are validated before the call and outputs after it; a failure is a tool result, never an exception that ends the run. A tool result as a tool message is the canonical JSON `{"ok": true, "result": ...}` or `{"ok": false, "error": {"code", "message", "details"?}}`.
- MCP over stdio only, with the `mcp` SDK 2.2.0 (protocol revision 2026-07-28, with fallback to the handshake revisions): the registry starts the server as a subprocess and records its PID, lists its tools, registers each as `<server>.<tool>` with the declared schema and the capability and side effect of the server's configuration entry (default `exec` and `write`; this project's servers are configured `none`), validates arguments against the schema before calling, and turns an MCP error result into `tool_error` (an error text `CODE: message` keeps the code), a protocol error or a server that exits into `tool_error` (`UNAVAILABLE` or `FAILED`), and a timeout into `tool_timeout`. At the end the server's stdin is closed; if it does not exit within 5 seconds, its process tree is killed by PID.

## 6. Workspace tools and permissions

- Workspace tools: `fs_read` (UTF-8 text, at most 65536 bytes per call with `offset` and `limit`; a binary file is refused), `fs_list`, `fs_write` (modes `create`, `overwrite`, `append`; parents inside the workspace are created), `fs_edit` (replace exactly one occurrence), `run_command` (an argument vector, no shell; the working directory is inside the workspace; the environment holds only `PATH`, `PATHEXT`, `SYSTEMROOT`, `SYSTEMDRIVE`, `WINDIR`, `TEMP`, `TMP`, `LANG`, `LC_ALL`, `PYTHONUTF8`, `PYTHONIOENCODING` when set; each output stream is cut at 65536 bytes with the marker `[... output truncated at 65536 bytes]`; on timeout, cancellation, and at the end of the run the process tree is killed by PID; a timeout is `tool_timeout`), `http_get` (text, at most 262144 bytes, redirects not followed, a timeout). `fs_read`, `fs_list`, `http_get` have side effect `read`; the others `write`. Capabilities: `fs_read`/`fs_list` -> `fs_read`, `fs_write`/`fs_edit` -> `fs_write`, `run_command` -> `exec`, `http_get` -> `net`. The tools of the simulated world and of the worked example declare `none`.
- **Path resolution** `resolve(root, path)` rejects, before touching the disk: an empty path, a NUL character, a drive letter, a UNC prefix, a device-namespace prefix (`\\?\`, `\\.\`), an absolute path, a leading `~`, a component that is a reserved device name (`CON`, `PRN`, `AUX`, `NUL`, `COM1`-`COM9`, `LPT1`-`LPT9`, with or without an extension), a component with a colon, a component that ends with a dot or a space. It then joins the path to the root, resolves symbolic links and junctions (`realpath`; for a path that does not exist yet the nearest existing ancestor), and requires the result to lie under the real path of the root (case-insensitively on Windows). This is a check at the time of the call: a link swapped in between the check and the use defeats it.
- **Decision** (pure function of the policy, the capability, and the resolved arguments `{"paths_ok", <path args as workspace-relative paths>, "argv", "host"}`); rows are tried from the top, the first that applies decides:

| Action | `read_only` | `workspace_write` | rule id |
|---|---|---|---|
| any path that resolves outside the workspace | deny | deny | `path_outside_workspace` |
| `exec` of an executable in `deny_exec` (or an empty argv) | deny | deny | `deny_exec` |
| capability `none` or `fs_read` | allow | allow | `capability_allowed` |
| `fs_write` inside the workspace | deny | allow | `read_only_sandbox` / `workspace_write` |
| `exec` starting with an `allow_exec` prefix | deny | allow | `read_only_sandbox` / `allow_exec_prefix` |
| any other `exec` | deny | ask | `read_only_sandbox` / `exec_needs_approval` |
| `net` to a host in `allow_hosts` | deny | allow | `read_only_sandbox` / `allow_hosts` |
| any other `net` | deny | ask | `read_only_sandbox` / `net_needs_approval` |

  The executable is matched by its file name without directory and extension, case-insensitively; an `allow_exec` prefix also matches the following arguments exactly. Default `deny_exec`: `cmd`, `powershell`, `pwsh`, `bash`, `sh`, `wsl`, `rm`, `rmdir`, `del`, `rd`, `format`, `diskpart`, `curl`, `wget`, `ssh`, `scp`, `ftp`, `nc`, `docker`, `sudo`, `reg`, `taskkill`, `shutdown`, `schtasks`. `ask` is settled by the approval mode: `ask` calls the approver (no approver: deny), `auto` allows, `never` denies; `approved_by` records who settled an `ask` (`approver`, `auto`, `never`, or `none` when there was no approver) and is null when no approval was involved. A denial that no approval can overturn (outside the workspace, `deny_exec`, `read_only`) never reaches the approver. A denied call does not run.
- Every decision for a tool whose capability is not `none` is a `permission` span; a denied call has no `tool` span. This is policy inside the process, not isolation by the operating system: `run_command` can do whatever its command can do under the account that runs the service, and the deny list of executable names guards against accidents, not attacks.

## 7. Context and the session log

- Events: `message` (`type`, `seq`, `id`, `run_id`, `conv`, `message` = the message fields) and `compaction` (`type`, `seq`, `id`, `run_id`, `conv`, `policy`, `covers_from`, `covers_to` as `seq` values, `replacement`, `tokens_before`, `tokens_after`). `replacement` is `{"drop": [seq...]}` (window), `{"stubs": {"<seq>": "<stub>"}}` (elide), or `{"summarize": [seq...], "summary": "<text>"}` (summarize). Conversations: `main` (shared by the runs of a session), `<run_id>/a<k>` for attempt k > 1, and for children `<run_id>/c<n>` (from `main`) or `<parent conversation>/c<n>`, so that no run sees another run's attempts or children. `fork(session, at_seq)` copies the log up to `at_seq` and the state.
- **Model-visible means logged.** The model's input is `derive_messages(events_of_conv, policy, budget_tokens)`: a pure function that applies the logged compactions in order. If the result exceeds `compact_at * budget` under a compacting policy, it also proposes a compaction that brings the input to at most `compact_to * budget`; the runtime logs it (after the summary call for `summarize`), writes a `context` span, and derives again. The `model` span records `agent_runtime.context.log_seq`, `.policy`, `.budget`, and `.messages_sha256`; rebuilding the request from the stored log reproduces the request digest.
- Units of compaction: an assistant message with tool calls and the tool messages that answer it form one exchange; other user and assistant messages are single units. Never compacted: system messages, the newest user message, the exchange in progress (the newest exchange after the newest user message). The last `keep_last` exchanges stay whole unless the budget forces them to be given up, one at a time, oldest first. `window` drops units; `elide` replaces tool results with stubs `[elided] result of <tool>(<args>) call <id> was removed to save space; call the tool again if you need it`; `summarize` replaces units with one assistant message starting `[summary]` produced by one billed and traced model call (role `summarize`, input: a fixed instruction and the covered messages).
- The part of the input a policy may not drop (it decides whether a target is offered): `none` everything; `window` the system prompt, the newest user message, and the exchange in progress; `summarize` those plus one summary of the rest; `elide` everything, with the tool results of every other exchange replaced by stubs.
- Token counters: the simulator's counter (500 per prompt, `result_tokens` per full tool result, 20 per stub, 100 per summary) is exact by construction; for real adapters the estimator (canonical-JSON bytes / 4, rounded up) decides about compaction only. Billing uses the usage the provider reports. The budget of a call is the chosen target's window minus `max_output_tokens`.

## 8. Subagents

`delegate(agent, task)` is a runtime tool (capability `none`, side effect `write`, never retried). The catalog maps a name to `description`, `system_prompt`, `tools` (a subset of the parent's tools; `delegate` only if listed and the depth allows), `target` (fixed) or the parent's router, `max_steps` (default 8), `max_cost_ucu`, `max_model_calls`. The child starts with its system prompt and the task only. What returns is `{"status", "text" (cut to 400 tokens = 1600 UTF-8 bytes with the marker ` [... cut to 400 tokens]`), "steps"}`; a child that ends otherwise returns `SUBAGENT_FAILED` with its status, reason, and steps. One meter: the child's calls are billed to the run; the child is bounded by its share and by what remains of the parent's budget. `max_depth` is 1 by default and at most 3. Tool calls of children share the run's concurrency limit (the `delegate` call itself does not hold a slot). A child is a `subagent` span (`agent_runtime.agent.name`, `.depth`, `.status`, `.steps`) under the `delegate` tool span; its spans have step paths that start at `<parent path>/c<n>`. Cancelling the parent cancels its children.

**Planner mode `delegate_plan`** (used by E6): one planning call; the plan's branches - the connected components of the plan without its tail, the tail being the join step (the first step, in plan order, with two or more dependencies) and every step that depends on it - run in parallel as `delegate` calls to child agents named `branch<n>` (tools: the branch's tools; target `sim-a/small` with the fallback `sim-a/medium`; `max_steps` = 2 x branch steps + 2); the parent then runs the tail steps with the list scheduler and writes the answer from the children's texts. A plan without a join step forms one branch.

## 9. Trace and replay

- One trace per run: JSON Lines (canonical JSON), one span per line in start order: `v` (1), `trace_id` (the run id), `span_id`, `parent_id`, `kind` (`run`, `step`, `model`, `tool`, `route`, `plan`, `validate`, `context`, `permission`, `subagent`), `name`, `start_ms`, `end_ms`, `status` (`ok`, `error`, `cancelled`, `failed`, `budget_exhausted`), `attrs`; `model` spans carry `request`/`response` and `tool` spans `args`/`result` with the SHA-256 of each one's canonical JSON (`request_sha256`, ...). A failed provider attempt is a `model` span whose response is `{"error": {...}}`.
- Attributes: GenAI names (semantic-conventions-genai commit b31e9e8e): `gen_ai.operation.name` (`chat`, `execute_tool`), `gen_ai.provider.name`, `gen_ai.request.model`, `gen_ai.usage.input_tokens` (all input, cached included, as the conventions define it), `gen_ai.usage.output_tokens`, `gen_ai.usage.cache_read.input_tokens`, `gen_ai.usage.cache_write.input_tokens`, `gen_ai.response.finish_reasons`, `gen_ai.tool.name`, `gen_ai.tool.call.id`, `error.type`. Others: `agent_runtime.cost_ucu`, `.attempt`, `.role`, `.step.path`, `.ordinal`, `.fallback`, `.retry`, `.origin_span`, `.route.policy`, `.route.chosen`, `.route.reason`, `.route.candidates`, `.context.tokens`, `.context.window`, `.context.budget`, `.context.policy`, `.context.conv`, `.context.log_seq`, `.context.messages_sha256`, `.permission.capability`, `.permission.decision`, `.permission.rule`, `.permission.approved_by`, `.permission.resolved`, `.permission.args_sha256`, `.agent.name`, `.agent.depth`, `.plan.step_ids`, `.validation.error`, `.verifier.accepted`; the `run` span records the run spec (`agent_runtime.config`), the status, the totals, and `agent_runtime.result_sha256`.
- `validate_trace`: exactly one `run` span, first; every parent exists and encloses its children; every span is closed; the run's cost equals the sum of all `model` spans; every tool call of a successful `model` span is answered by exactly one `tool` span or a denying `permission` span (unanswered calls are allowed only in runs that ended `failed`, `cancelled`, or `budget_exhausted`, and inside a `subagent` span that did not end ok); every `tool` span answers a call of a `model` span, a step of a `plan` span, or a runtime call of a `step` span.
- Replay re-executes the workflow from the recorded spec on a virtual clock with a recorded model, recorded tools, and a recorded approver, matched by (step path, kind, ordinal) and checked against the request and argument digests; permission decisions are decided again on the recorded resolved arguments and must agree; where the replay environment knows a tool, its allowlist, argument validation, and capability are checked against the record (a permission span exactly when the capability is not `none`), and a denied call's argument digest must match; `delegate` runs again (its children's calls are recorded). It must reproduce the span sequence (kind, name, parent, status, attributes except store-assigned ids, digests, and, for virtual-clock traces, times) and the result digest, with zero provider and zero tool calls; otherwise it raises `ReplayDivergence` naming the first differing span. Replay is unavailable when payload capture was off.

## 10. Simulator (assumptions)

| Model | Price in / out (cu per 1M tokens) | Latency (ms) | P(correct call) easy / medium / hard | Context (tokens) |
|---|---|---|---|---|
| `small` | 0.15 / 0.60 | 200 + 8 per output token | 0.92 / 0.55 / 0.15 | 4096 |
| `medium` | 1.00 / 4.00 | 500 + 15 per output token | 0.98 / 0.85 / 0.50 | 16384 |
| `large` | 5.00 / 20.00 | 1200 + 30 per output token | 0.995 / 0.96 / 0.82 | 32768 |

- Providers `sim-a` and `sim-b` serve the same three models with the same numbers. Latency is multiplied by a lognormal factor (median 1, sigma 0.2). A cache read costs 10% of the input price (cache off by default).
- Tokens: the prompt is 500 tokens plus `result_tokens` (default 250) per tool result in full, 20 per stub, 100 per summary; the completion is 80 per tool call, 60 + 40 per step for a plan or replan, 100 for a summary, 120 for a final answer. An input over the model's window is answered with `context_length` and not billed.
- A call derives its action from the task's gold plan and the conversation in its request and is correct with the probability of the table for the task's tier. A wrong call is invalid with probability 0.3 (unknown tool or arguments of a wrong type; validation always catches it), names an entity that does not exist with probability 0.3 (`NOT_FOUND`), and is silent with probability 0.4 (plausible wrong arguments that return valid but wrong data). A call that depends on a wrong (silent) result is itself silent-wrong, so the final answer of such a run is wrong; only the verifier can signal it. A wrong final answer is a perturbed copy of the gold answer. In a plan every step is drawn independently with the same probability, so the planner modes have the same per-step accuracy and differ in calls, latency, cost, and recovery.
- Visibility: a call whose step depends on earlier results is correct only if each is visible: in full; inside a summary (each fact survives with probability `keep` = 0.9); as a stub (the model first repeats that read); dropped by `window` (the call is wrong and silent).
- World (`world_seed` 1): 200 customers, 600 products (list prices in USD), 2000 orders (1-6 items), currencies USD, EUR, GBP, JPY, CNY with fixed rates. Read tools `get_customer`, `list_orders`, `get_order`, `get_product`, `convert`, `calc` (latencies 300, 350, 250, 250, 100, 20 ms), write tool `send_report` (400 ms), all times the lognormal factor. Two identical writes are a duplicate.
- Tasks `gen(seed, n, mix, shape)`: templates lookup (`get_customer`), unit price (order -> product), order value (order -> products -> `calc` -> optional `convert`), multi-order value (`list_orders` -> orders -> products -> `calc` -> optional `convert`), each followed by `send_report` for 20% of the tasks. Tier by steps: easy 1-2, medium 3-5, hard 6-8. Mixes `mixed` (50/35/15%) and `hard_heavy` (15/35/50%). Shape `chain`: dependent steps in sequence; shape `wide`: fan-out of width 2-4 with 4-10 steps (a drawn easy tier maps to 4 steps, medium to 5, hard to 6-10; a task with a report has at least 5 steps; the tier label follows the step count, so 4-5 steps are medium and 6-10 hard). The hint is the tier index (1-3) plus Gaussian noise with sigma 0.6. Plan arguments are literal values.
- Verifier: rejects a wrong final answer with probability `recall` (0.7) and never rejects a right one.
- Delegation (E6): a child (task id `<task>/c<n>`) works on the gold steps of branch n of the task's gold plan (the parent's plan arguments are not used by the simulated child); its final text carries its branch's facts with probability `keep_delegate` (0.95); a parent that is missing any branch's facts answers wrong.
- Faults (E2): `calm` 5xx 0.5%; `flaky` 5xx 6%, 429 3% (`retry_after_ms` 1000), timeouts 2% (the call hangs past the 10000 ms timeout); `brownout` = calm plus every `sim-a` call that starts between 150 s and 270 s of the experiment clock fails with 5xx. A 5xx or 429 answers after 100 ms.

## 11. Metrics and statistics

Per task: `success` (the checker accepts the final answer, and the world saw no duplicate write and no write with wrong arguments), `accepted` (no validation failure left and the verifier did not reject), `cost_ucu` (a call that returned a response is billed, wrong or malformed included; provider errors are not), `latency_ms` (run start to run end), `model_calls`, `tool_calls`, `provider_calls` (failed attempts included), `retries`, `fallbacks`, `repairs`, `replans`, `escalations`, `status`, `failure_reason`, `peak_context_tokens`, `compactions`, `repeat_reads`, `cache_read_tokens`, `subagent_runs`, `duplicate_writes`, `wrong_writes`, `bound_gap` (plan modes: tool-phase duration / `max(CP, W/k)` of the executed steps). Per seed: means over tasks; P50 and P95 of latency (linear interpolation). Across seeds: mean and 95% Student-t interval (`t.ppf(0.975, n-1) * sd / sqrt(n)`); for P95, the mean of the per-seed P95. Paired differences against a reference on common seeds; win/tie/loss per seed with tie bands 0.01 absolute for success and 2% relative for cost and latency; a win is better on the primary metric beyond its band and not worse beyond its band on any guard metric; a loss is worse on the primary beyond its band, or within its band on the primary and worse beyond its band on a guard; everything else (including a trade-off) is a tie.

## 12. HTTP API

Endpoints: `GET /healthz`; `GET /v1/models`; `GET /v1/tools`; `GET /v1/usage`; `POST /v1/sessions` (201); `GET /v1/sessions/{id}`; `PUT /v1/sessions/{id}/state` (`expected_version`, `state`); `POST /v1/sessions/{id}/fork` (`at_seq`; 201); `GET /v1/sessions/{id}/context?policy=&window=` (a dry derivation of the main conversation that writes nothing); `POST /v1/runs` and `POST /v1/sessions/{id}/runs` (`{"workflow", "input", "config"}`; 202 with the run id, or the finished run with `?wait=true`); `GET /v1/runs/{id}`; `GET /v1/runs/{id}/trace` (JSON Lines); `POST /v1/runs/{id}/cancel`; `POST /v1/runs/{id}/replay` (`{"divergence": null, ...}` or the divergence report). ## 13. Optimization agent (worked example)

- Problem card (JSON): `id`, `kind`, `statement` (at most 150 words), `data`, `variables` (name -> meaning; the formulation must use these names and may add auxiliary variables), `witnesses` (each `point` over the card's variables, `feasible`, `note`), `tolerances` (`feasibility` 1e-6, `integrality` 1e-6, `objective_abs` 1e-6, `objective_rel` 1e-6, `report_abs` 1e-4). Formulation: `sense` (`min|max`), `variables` (`name`, `lb`, `ub` (null = unbounded), `type` (`continuous|integer|binary`)), `objective` (`terms`, `constant`), `constraints` (`name`, `terms`, `sense` (`<=|>=|==`), `rhs`).
- Workflow: `formulate` (structured output) -> `opt.solve` -> `opt.verify`; a rejection sends the diagnostics back (at most 2 repairs); then `report` (structured output `{objective, values}`) -> `opt.check_report`; a mismatch sends one re-ask. Solver: SciPy `milp` (HiGHS); a MIP that HiGHS reports as "unbounded or infeasible" is classified by a feasibility solve.
- Verifier codes: V1 `V1_PARSE`, `V1_DUPLICATE_NAME`, `V1_UNDECLARED_VARIABLE`, `V1_NONFINITE`, `V1_BOUNDS`, `V1_MISSING_CARD_VARIABLE`; V2 `V2_INFEASIBLE`, `V2_UNBOUNDED`, `V2_SOLVER_ERROR`; V3 `V3_BOUND`, `V3_INTEGRALITY`, `V3_CONSTRAINT`, `V3_OBJECTIVE`; V4 `V4_FEASIBLE_WITNESS_REJECTED` (with the card's variables fixed, within the formulation's own bounds, and the auxiliary variables solved for), `V4_WITNESS_BEATS_OPTIMUM`, `V4_INFEASIBLE_WITNESS_ACCEPTED`; V5 `V5_REPORT_MISMATCH`. What the verifier does not check is listed in `docs/optimization-agent.md`.

## 14. Skills

A skill is a directory with a `SKILL.md` whose front matter (between `---` lines) has `name`, `description`, and an optional `tools` list; the body is the instructions. The system prompt of the react-family workflows carries only the catalog (`- <name>: <description>`, one line per skill); the tool `load_skill(name)` (capability `none`, side effect `read`) returns `{name, tools, body}` with the body cut at 2000 tokens (8000 UTF-8 bytes); an unknown name is `NOT_FOUND`. The run's meter counts `skill_catalog_tokens` and `skill_body_tokens` (estimator tokens).
