# Evaluation (simulated)

Every number in this document comes from runs of the simulator described in [contracts.md](contracts.md) section 10. The models' accuracies, prices, and latencies are **assumptions**; the results say how the runtime and its decision rules behave under those assumptions, "in this simulation, under these assumptions", and nothing about hosted models. The tasks are far simpler than real agent tasks; they exist to exercise and measure the runtime.

## Protocol (fixed before the full evaluation; the later changes are listed under Results)

- **Seeds.** Tuning seeds 1-10; evaluation seeds 101-130 (E1-E3, E5, E6); sensitivity seeds 101-110 (E1, E6). Common random numbers: the tasks of a seed are identical for every configuration.
- **Statistics.** Per seed: means over tasks, P50 and P95 of latency (makespan). Across seeds: mean and 95% Student-t interval. Paired differences against the named reference on common seeds, with Student-t intervals. Win/tie/loss per seed with tie bands 0.01 absolute (success) and 2% relative (cost, latency). Dominance rule: a configuration wins a seed when it is better on the primary metric beyond its band and not worse beyond its band on any guard metric; it loses when it is worse on the primary beyond its band, or within its band on the primary and worse beyond a band on a guard (dominated); otherwise tie, including a trade-off (better on the primary, worse on a guard). This rule replaced an earlier one (a trade-off counted as a loss, a dominated configuration as a tie) after Review 1, before the full evaluation; a quick run with the earlier rule had been committed before the change. Primary / guards: E1 success / cost; E2 success / P95 latency and cost; E3 makespan P50 / success and cost; E5 success / cost and P95 latency; E6 success / cost and makespan P50.
- **E1 budget levels.** From the tuning seeds, before any other router ran: mean cost of `fixed(small)` 1087 ucu and of `fixed(large)` 29603 ucu; four levels spaced geometrically inside that range, `B_i = small * (large/small)^(i/5)`: B1 = 2106, B2 = 4077, B3 = 7895, B4 = 15288 ucu.
- **E1 tuning.** Every tunable router evaluated once per configuration on the tuning seeds (300 tasks each): `random_mix` probabilities on a grid of step 0.25 (15 configurations), `cascade` chains small-medium-large, small-large, medium-large (3), `threshold` `t1 <= t2` from {0.5, 1.0, 1.5, 2.0, 2.5, 3.0} (21). These are the grids the protocol names; the search sizes are unequal (21, 15, 3), which favours the families with larger grids in the selection, and the README `## TODO` notes them. For each B: the configuration with the highest mean success whose mean cost is at most B (ties: lower cost, then index). The selections are frozen in [`configs/e1_frozen.json`](../configs/e1_frozen.json). No router has a configuration within B1 or B2 except `random_mix`: `threshold` sends every hint >= t2 (at most 3.0) to `large`, and a cascade starting at `small` costs more than B2 on the tuning seeds. The grid was kept as planned.
- **Informativeness check** (tuning seeds; [`results/informativeness.csv`](../results/informativeness.csv)): the spread of the main metric across configurations against the largest standard error across seeds. E1 at B1 and B2 has one router within budget, so nothing is ranked there; B3 separates (success spread 0.207 vs SE 0.010); B4 does not (0.0070 vs 0.0108), so it is reported and not ranked. E2 `calm` separates only marginally (0.013 vs 0.011); `flaky` (0.236 vs 0.010) and `brownout` (0.158 vs 0.012) clearly. E3 separates clearly in makespan (4.52 s vs 0.15 s) and success (0.110-0.113 vs 0.011). E5 ([`results/e5/informativeness.csv`](../results/e5/informativeness.csv), `none` and the three selected policies): `small`/1500 (0.100 vs 0.010), `small`/3000 (0.142 vs 0.009), and `medium`/3000 (0.037 vs 0.012) separate; `small`/250, `medium`/250 (spread 0), and `medium`/1500 (0.002 vs 0.012) do not and are not ranked. E6 ([`results/e6/informativeness.csv`](../results/e6/informativeness.csv), computed once with the E6 jobs on the tuning seeds by an inline call, not a CLI command, before the context fix described under Results, which changes the target of some `react_small_elide` steps; it was not re-run): success 0.468 vs 0.013, makespan P50 3.01 s vs 1.54 s.

## Experiments

- **E1 Routing under a cost budget.** Task set `mixed`, planner `react`, `sim-a` without faults, 300 tasks per seed, run deadline 30000 ms (no call starts after it; a run stopped by the deadline ends `budget_exhausted` and counts as a failure, but a call already in flight may finish after it, so P95 latencies above 30 s occur). Routers `fixed(small|medium|large)`, `random_mix`, `cascade` (budget-aware: no attempt that cannot finish before the deadline at the next model's median latency times the calls of the previous attempt), `threshold`, and the offline `oracle` (per task the cheapest successful fixed run, else the cheapest; an upper bound for routing that picks one model per task, which cannot be implemented; a cascade's second attempt is a new draw and can succeed where every fixed run failed). Paired differences against `random_mix` at the same B. Sensitivity (seeds 101-110, B3, each row re-tuned on the tuning seeds): hint sigma 0.3 and 1.2, verifier recall 0.5 and 0.9, the `hard_heavy` mix.
- **E2 Reliability under provider faults.** Task set `mixed`, `fixed(medium)`, `react`, Poisson arrivals at 0.5 tasks/s for 600 s (about 300 tasks), at most 16 runs in flight, timeout 10000 ms, no deadline. Profiles for `sim-a` (`sim-b` calm in all): `calm`, `flaky`, `brownout`. Configurations `no_retry`, `retry` (defaults), `retry_fallback` (then `sim-b`). Reference: `retry`.
- **E3 Planning and scheduling.** Task set `mixed`, shape `wide`, `fixed(medium)`, 200 tasks per seed, planner modes `react`, `react_parallel`, `plan_execute`, `plan_replan`, k in {1, 2, 4, 8} for the parallel modes, transient read-tool failure 0% and 10% (`UNAVAILABLE`, retried twice). Reference: `react`. The modes share their per-step accuracy in the simulation, so E3 compares calls, latency, cost, and recovery, not the planning quality of real models.
- **E4a Optimization agent.** The six problems end to end with the scripted model and the MCP server on the system clock ([optimization-agent.md](optimization-agent.md)).
- **E4b Verifier study (Tier 2).** Ten mutation operators (drop a constraint, reverse an inequality, scale a coefficient by 10 or 0.1, change a right-hand side, change a bound, drop integrality, swap the objective sense, rename a variable, add a constraint) applied to the six reference formulations, 5 seeded mutants per operator and problem (stream `mutate/<problem>/<operator>/<k>`; operators that do not apply are skipped). Ground truth with the reference outside the workflow: a mutant is wrong if its optimum is infeasible for the reference (the card's variables fixed), its objective differs from the reference optimum beyond the tolerance, it has no optimum, or it renames a card variable; otherwise it is equivalent at the optimum. Verifier configurations: no witnesses, the first 2 witnesses, all witnesses. Reported per operator and configuration: detection rate on wrong mutants, false-reject rate on equivalent ones, and the wrong mutants that every configuration accepts. The claim is limited to these injected mutations.
- **E5 Context policies (Tier 2).** Task set `mixed`, shape `chain`, `react`, 200 tasks per seed. Setups `small` (fixed small with the fallback medium, used when small is not offered because its window cannot hold the input's irreducible part) and `medium`; summaries by `small`. Result sizes 250, 1500 (primary), 3000; prefix cache off and on. Configurations `none`, `window`, `elide`, `summarize` (each with keep_last {1,2,3} x compact_to {0.4,0.5,0.6}, compact_at 0.75), tuned per (setup, size) on the tuning seeds with the cache off (highest success; ties: lower cost, then index; the selection is reused with the cache on, which changes cost, not outcomes), plus the ablation `elide` with compact_to = compact_at (compaction at every step). Reference `none`. Selections in [`configs/e5_frozen.json`](../configs/e5_frozen.json); informativeness per scenario in `results/e5/informativeness.csv`.
- **E6 Delegation (Tier 2).** Task set `mixed`, shape `wide`, result_tokens 1500, cache off, 200 tasks per seed. `react_small_elide` (fixed small, fallback medium, the E5 elide selection for (small, 1500)), `react_medium`, `react_parallel_medium_k4`, `delegate` (a medium planning call; the plan's branches - the connected components of the plan without its tail, the tail being the join step and everything after it - run in parallel as child `react` agents on small with the fallback medium; the parent runs the tail and writes the answer from the children's texts). In the simulation a child works on the gold steps of its branch, and its final text carries the branch's results with probability `keep_delegate` = 0.95 (sensitivity 0.8 and 1.0 on seeds 101-110); a parent missing a branch's results answers wrong. Single-order wide tasks share their `get_order` root and form one branch, so delegation degenerates there. Reference `react_medium`.
- **E7 Live validation (Tier 2).** Not run: no endpoint configured (`scripts/live_smoke.py` printed `not run: no endpoint configured`).

## Results

The result tables are in [`results/tables.md`](../results/tables.md) (generated from the CSV files in `results/`), the figures in `docs/figures/`; the findings are summarized in the README. They come from one run of `eval --full --workers 8` on commit `5240bef` (1837 s; no other agent run active; CPU load from the owner's jobs 22%); later code changes (the report writes its tables, the manifest records the commit at the start of a run, the API accepts only the documented workflows) touch no experiment. The E1 budget levels and selections and the E5 selections come from the earlier tuning runs (`results/e1/manifest_tuning.json`, `results/e5/manifest_tuning.json`, and the sensitivity variants' own tuning manifests). The full evaluation ran twice: the first run (commit `e89c7ae`, 4 workers, 3128 s) showed `context_length` failures in E5 where a summary or stubs should have let a step move to the larger window (the part of the input a policy may not drop did not count them); after the fix (`5c439c2`) E5 was re-tuned (`5240bef`, only the `small`/3000 selections changed) and the whole evaluation was run again. The per-task rows of E1-E3, trace digests included, were byte-identical between the two runs (4 and 8 workers); this was checked at the time and cannot be re-checked from the committed files, because nothing of the first run is committed.

## Reproduce

```bash
python -m agent_runtime eval --experiment e1-tune --workers 4
python -m agent_runtime eval --experiment informativeness --workers 4
python -m agent_runtime eval --experiment e5-tune --workers 4
python -m agent_runtime eval --full --workers 4
python -m agent_runtime report
```

E2, E3, E5, and E6 write `results/<experiment>/summary.csv` (one row per configuration and seed), `aggregate.csv`, `paired.csv` (paired differences and win/tie/loss), and E2 also `brownout_windows.csv`; E1 and each sensitivity variant write `summary.csv` and `table.csv` (with the paired columns) plus the tuning files; E4 writes `table.csv`; E4b writes `summary.csv` (per operator and witness configuration), `mutants.csv`, and `missed_by_all.csv`. Each writes a `manifest.json` with the commit, the configuration hash, the seeds, the Python and library versions, the worker count, and the load note; per-task rows go to the ignored `eval-results/`.
